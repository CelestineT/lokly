# Recette du 17 octobre 2026 — Ekolocs

## Activation des nouveaux champs

Exécuter `supabase/migrations/20261017_suivi_paiements_financements.sql` dans le projet Supabase utilisé par cet environnement. La migration est additive et réexécutable : aucun enregistrement existant n'est supprimé. Elle ajoute le solde antérieur sur les paiements, la note interne du locataire et les postes à financer.

Avant migration, les parcours existants restent utilisables. L'enregistrement d'un nouveau champ non disponible affiche une explication ; il n'est pas remplacé par une sauvegarde locale ou un commentaire public.

## Vérifications

```sh
node tests/payment-regressions.cjs
node tests/document-financing-regressions.cjs
npx tsc --noEmit
npm run build
```

- Modifier un paiement existant : montant, mois, date, mode, statut et commentaire ; sauvegarder puis recharger.
- Saisir 0 € et 100 € de solde antérieur pour un mois de 850 € : le mois impayé reste distinct, le reste global vaut 950 €, aucune recette fictive n'est créée.
- Tester un ancien locataire : enregistrer un paiement pour une période passée, puis créer la quittance si le mois est acquitté.
- Couple : les paiements des deux occupants sont additionnés une seule fois ; un lot annexe n'est présenté qu'une seule fois.
- Message PDF : les deux commentaires subsistent sans préfixes ajoutés « Quittance : » ou « Paiement : ».
- Note interne : enregistrée sur le locataire, jamais transmise au générateur PDF ou aux e-mails.
- Financement : travaux, mobilier, terrain ; supprimer un poste puis sauvegarder ; la mensualité et le montant emprunté ne sont pas modifiés automatiquement.
- À vérifier sur appareils réels : Chrome et Safari, ouverture/défilement/sauvegarde de la fenêtre de modification, sélection mois/date, absence de débordement horizontal, menu mobile.

## E-mails : activation explicite en production

Le mode de recette reste le comportement par défaut. Aucun e-mail de test n'a été réellement envoyé pendant les vérifications automatisées.

Configurer dans Vercel, uniquement sur l'environnement où l'envoi réel est souhaité :

```text
RESEND_API_KEY=<clé Resend>
RESEND_FROM_EMAIL=Ekolocs <quittances@votre-domaine-verifie.fr>
QUITTANCE_EMAIL_MODE=production
```

Vérifier le domaine d'envoi dans Resend et ses enregistrements DNS avant activation. L'adresse ci-dessus est un exemple à remplacer. Le code de confirmation est alors envoyé au bailleur connecté ; après confirmation, le PDF part au locataire avec une copie cachée au bailleur. Les adresses proviennent de leurs comptes/fiches respectifs. Ne pas renseigner la clé privée dans une variable `NEXT_PUBLIC_*`.

En recette, `QUITTANCE_TEST_EMAILS` ou `QUITTANCE_TEST_EMAIL` permet de choisir la boîte de test autorisée par Resend. Avec `onboarding@resend.dev`, Resend limite l'envoi à l'adresse du compte Resend. Le mode recette continue de présenter le code de test dans l'interface.

L'acceptation par l'API Resend n'est pas une preuve de livraison en boîte de réception : vérifier les événements Resend et les indésirables.

La route historique `/api/youtrust` est un parcours sandbox distinct ; elle n'est pas utilisée par la confirmation et l'envoi de quittance actuels. Les SMS groupés ne sont pas implémentés dans cette livraison ; ils nécessitent un fournisseur SMS et une intégration séparée.
